# V-03 · SSRF en `/api/vehicles/{id}/webhook`

| Campo | Valor |
|---|---|
| **ID** | V-03 |
| **Título** | Server-Side Request Forgery: la app hace requests a URLs controladas por el usuario sin validar destino |
| **Severidad** | 🟠 **HIGH** |
| **CVSSv3.1** | **8.6** |
| **Vector** | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:N/A:N` |
| **CWE** | [CWE-918](https://cwe.mitre.org/data/definitions/918.html) · Server-Side Request Forgery (SSRF) |
| **OWASP Top 10 2021** | [A10:2021 – Server-Side Request Forgery](https://owasp.org/Top10/A10_2021-Server-Side_Request_Forgery_%28SSRF%29/) |
| **OWASP ASVS 4.0.3** | V12.6.1 (SSRF protection / allowlist de destinos) |
| **Estado** | **Open** _(se actualiza a Fixed en FSEC-17)_ |

---

## Affected

- **Endpoint:** `POST /api/vehicles/{id}/webhook`
- **Componente:** [`VehicleController.webhook()`](../../app/src/main/java/co/fleetsec/vapp/web/VehicleController.java) — usa `HttpClient.send()` sobre la `url` del body sin validación.

## Description

El endpoint de webhook de telemetría toma una `url` del body y hace un **GET server-side** a ese destino, devolviendo la respuesta al cliente. No hay allowlist de host ni bloqueo de rangos privados/link-local:

```java
HttpRequest request = HttpRequest.newBuilder().uri(URI.create(url)).GET().build();  // url del atacante
HttpResponse<String> response = httpClient.send(request, ...);                       // fetch server-side
return ResponseEntity.ok(Map.of(..., "body", response.body()));                      // respuesta reflejada
```

Un atacante usa la app como **proxy** para alcanzar recursos internos que no puede tocar directamente — incluido el endpoint de metadata de la instancia cloud (`169.254.169.254`).

## CVSSv3.1 — justificación métrica por métrica

`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:N/A:N` → **8.6 (High)**

| Métrica | Valor | Justificación |
|---|---|---|
| **AV** | **N** | Endpoint HTTP remoto. |
| **AC** | **L** | Enviar una `url` en el body; sin condiciones. |
| **PR** | **N** | Sin auth (ver V-11). |
| **UI** | **N** | Sin interacción. |
| **S** | **C** (Changed) | **Clave:** el componente vulnerable (la app) se usa para atacar un componente en **otra authority de seguridad**. La app, con su identidad/red interna, alcanza el **metadata endpoint de la instancia** (`169.254.169.254`) o servicios internos — recursos gobernados por la authority del entorno cloud/red, no por la de la app. El impacto trasciende el scope de la app hacia el de la infraestructura. |
| **C** | **H** | En el entorno AWS de FleetSec (ECS/EC2, Entregable 03), IMDS devuelve **credenciales IAM temporales** de la instancia → compromiso de la cuenta cloud. Demostrado localmente: fetch server-side a servicios internos + intento a link-local sin validación. |
| **I** | **N** | El vector demostrado es GET (lectura); sin escritura. |
| **A** | **N** | Sin impacto de disponibilidad directo. |

> **Justificación del Scope:C** (lo que más sube el score): SSRF permite que la app —que sí tiene acceso a la red interna y a IMDS— actúe en nombre del atacante externo. El recurso impactado (metadata/credenciales de la instancia) pertenece a la **authority del entorno cloud**, distinta de la authority de la aplicación. Ese cruce de authorities es la definición de Scope:Changed.

## PoC

> Base: [`app/smoke-tests.http`](../../app/smoke-tests.http) (bloque V03). Ejecutado el 2026-08-02.

**Test 1 — fetch server-side a un servicio interno** (el atacante no lo alcanza directo):
```bash
curl -s -X POST http://localhost:8080/api/vehicles/1/webhook -H "Content-Type: application/json" \
  -d '{"url":"http://localhost:8080/v3/api-docs"}'
# → {"status":200,"body":"{\"openapi\":\"3.0.1\",...}"}   ← la app hizo el request server-side
```

**Test 2 — intento a IMDS de AWS** (sin validación de destino):
```bash
curl -s -X POST http://localhost:8080/api/vehicles/1/webhook -H "Content-Type: application/json" \
  -d '{"url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/"}'
# Local (sin cloud): {"error":"No se pudo contactar el webhook: null"}  ← la app INTENTA la conexión link-local
# En EC2/ECS: devolvería el rol IAM + credenciales temporales de la instancia
```
El error de conexión confirma que la app **envía** la request a `169.254.169.254` sin bloquear el rango link-local; en el entorno cloud real el fetch tendría éxito.

### Por qué el scanner NO lo caza

- **DAST (ZAP):** la regla Cloud Metadata quedó PASS — el destino va en un **body JSON** (`{"url":...}`) sobre un schema `Map` sin properties, así que ZAP no inyecta la URL de IMDS. **SAST:** no hay taint desde `url` del body al `HttpClient` en los rulesets usados.
- → Detectable por **análisis manual** + PoC dirigido.

## Impact

- **Confidencialidad (Alta):** en el entorno AWS de FleetSec, robo de **credenciales IAM temporales** vía IMDS → pivot a la cuenta cloud (buckets con PII, RDS, etc. — ver Entregable 03/04). Acceso a servicios internos no expuestos.
- **Interacción:** encadena con el escenario de breach del Entregable 04 (exfiltración desde S3 con credenciales robadas).
- **Integridad/Disponibilidad:** no demostradas por este vector.

## Remediation

- **Allowlist de destinos** (host/dominio) para webhooks; rechazar todo lo demás.
- Bloquear rangos privados y link-local: `169.254.0.0/16`, `10/8`, `172.16/12`, `192.168/16`, `127/8`.
- Forzar **IMDSv2** (hop limit + token) en las instancias (Entregable 03) como defensa en profundidad.
- Validar esquema (`https` solamente) y resolver DNS antes de conectar (evitar rebinding).

**Test dual (FSEC-17):**
1. **Rechazo:** `url=http://169.254.169.254/...` (o `http://10.0.0.1`) → `400`, sin fetch.
2. **Flujo legítimo OK:** `url=https://webhook.allowlisted.example/...` → fetch permitido.
