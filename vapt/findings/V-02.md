| Campo | Valor |
|---|---|
| **ID** | V-02 |
| **Título** | La validación de JWT confía en el `alg` del cliente y acepta tokens sin firma (`alg:none`) |
| **Severidad** | 🟡 **MEDIUM** |
| **CVSSv3.1** | **6.5** |

## Affected

- **Endpoint:** `POST /api/auth/validate` ([`AuthController.java:78-79`](../../app/src/main/java/co/fleetsec/vapp/web/AuthController.java#L78-L79))
- **Componente:** [`JwtService.validateToken()`](../../app/src/main/java/co/fleetsec/vapp/security/JwtService.java#L71) — rama `alg:none` (~línea 82)

## Description

`JwtService.validateToken()` lee el campo `alg` del **header controlado por el cliente** y, si vale `none`, devuelve los claims **sin verificar firma**:

```java
// JwtService.java (validateToken)
String alg = header.path("alg").asText("");     // línea 80
if ("none".equalsIgnoreCase(alg)) {             // VULN V02
    return claimsFrom(payload);                 // acepta el token forjado tal cual
}
```

Se implementó JWT a mano precisamente porque las librerías modernas (jjwt, nimbus) rechazan `alg:none` por defecto. Un atacante forja `{"alg":"none"}.{"sub":"admin","role":"ADMIN"}.` (sin firma) y el servicio lo acepta como identidad válida.

## CVSSv3.1 — justificación métrica por métrica

`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N` → **6.5 (Medium)**

> Criterio: score **estricto por impacto directo demostrado**. En el estado actual, ningún endpoint enforcea el token (ver [V-11](V-11.md)), así que forjar una identidad **no desbloquea recursos protegidos**. El impacto directo es bajo/medio — el primitivo de auth está roto pero no gatea nada todavía.

| Métrica | Valor | Justificación (demostrada) |
|---|---|---|
| **AV** | **N** | Endpoint HTTP remoto. |
| **AC** | **L** | Forjar el token es trivial (base64, sin firma). |
| **PR** | **N** | No requiere credenciales. |
| **UI** | **N** | Sin interacción de víctima. |
| **S** | **U** | Dentro de la authority de la app. |
| **C** | **L** | El endpoint de validación acepta y refleja una identidad forjada (`sub`, `role`); fuga limitada de la confianza del mecanismo. Nada protegido se desbloquea hoy. |
| **I** | **L** | Se puede afirmar una identidad admin falsa ante el mecanismo de auth; sin consumidor que la enforce, el impacto de integridad directo es bajo. |
| **A** | **N** | Sin impacto de disponibilidad. |

## PoC

> Base: [`app/smoke-tests.http`](../../app/smoke-tests.http) (bloque V02). Ejecutado el 2026-08-02.

Token forjado con `alg:none` (sin firma), reclamando `sub=admin, role=ADMIN`:
```
header  = {"alg":"none","typ":"JWT"}          → eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0
payload = {"sub":"admin","role":"ADMIN"}      → eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJBRE1JTiJ9
```
```bash
curl -s -X POST http://localhost:8080/api/auth/validate -H "Content-Type: application/json" \
  -d '{"token":"eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJBRE1JTiJ9."}'
# → {"role":"ADMIN","sub":"admin","valid":true}   ← token SIN firma ACEPTADO
```

### Por qué el scanner NO lo caza (aquí el pentest agrega valor)

- **SAST (Semgrep):** los rulesets `p/java`/`p/owasp-top-ten` no modelan "acepta `alg:none`" en una implementación **manual** de JWT; no hay pattern para esta lógica custom. Las custom rules del proyecto apuntan a V05/V09/V10, no a esto.
- **DAST (OWASP ZAP):** no forja tokens `alg:none` por sí solo; no hay regla activa que construya este payload de negocio.
- → Vector **solo detectable por análisis manual** del código y forja dirigida del token.

## Impact

- **Directo (actual):** el mecanismo de verificación de JWT está roto — acepta identidades forjadas. Impacto acotado porque nada consume el token para autorizar (ver [V-11](V-11.md)).
- **⏰ Bomba de tiempo (interacción con V-11) — el punto clave:** la remediación natural de V-11 es **activar enforcement de auth** (exigir un JWT válido en los endpoints). Si eso se hace **sin** remediar V-02, el JWT débil se convierte en **EL vector de account takeover**: cualquiera forja `alg:none` con `role:ADMIN` y obtiene acceso total. El impacto salta a **C:H/I:H (~9.1)**.
- **Orden de remediación (para el reporte Sprint 2):** arreglar V-02 (y [V-10](V-10.md)) **antes o junto con** activar el enforcement de V-11 — nunca después.

## Remediation

Verificar **siempre** la firma y fijar el algoritmo esperado; rechazar `alg:none`:

```java
// Usar una librería estándar (jjwt/nimbus) que rechaza alg:none, con algoritmo fijo:
Jwts.parser().verifyWith(hmacKey).build().parseSignedClaims(token);   // rechaza alg:none y firmas inválidas
// o, en la impl manual: eliminar la rama alg:none y exigir HS256 + verificación HMAC constante.
```

**Test dual (implementado · commit `b320fd8`):**
1. **Rechazo:** `AuthSecurityRemediationTest.v02_algNoneTokenFromPoc_isRejected` — el token `alg:none` **exacto de la PoC** → `401 valid:false`.
2. **Flujo legítimo OK:** `AuthSecurityRemediationTest.v02_validHs256Token_isAccepted` — un JWT HS256 válido emitido por la app → `valid:true`.
