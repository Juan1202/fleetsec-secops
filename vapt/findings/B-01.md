# B-01 · Ausencia de HTTP security headers (clickjacking / MIME-sniffing / sin CSP·HSTS)

| Campo | Valor |
|---|---|
| **ID** | B-01 _(hallazgo bonus — FSEC-19)_ |
| **Título** | La app no emite headers de seguridad (X-Frame-Options, CSP, HSTS, X-Content-Type-Options, Referrer/Permissions-Policy) |
| **Severidad** | 🔵 **LOW** |
| **CVSSv3.1** | **3.1** |
| **Vector** | `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N` |
| **CWE** | [CWE-693](https://cwe.mitre.org/data/definitions/693.html) · Protection Mechanism Failure |
| **OWASP Top 10 2021** | [A05:2021 – Security Misconfiguration](https://owasp.org/Top10/A05_2021-Security_Misconfiguration/) |
| **OWASP ASVS 4.0.3** | V14.4.1/.3/.5/.7 (HTTP security headers) |
| **Estado** | ✅ **Fixed** (2026-08-03 · commit `0927e6e`, FSEC-17 PR-C) — con residual Low documentado |

---

## Affected

- **Componente:** [`SecurityConfig`](../../app/src/main/java/co/fleetsec/vapp/config/SecurityConfig.java) — en la baseline **no existía** ninguna política de headers; **todas** las respuestas HTTP se servían sin ellos.
- **Alcance:** cualquier respuesta de la API (`/api/**`) + la Swagger UI (`/swagger-ui/**`, HTML framable).

## Description

En la baseline (pre-Sprint 2) la aplicación no configuraba ningún security header. Cada respuesta
—incluyendo la Swagger UI, que es HTML renderizable— se servía sin `X-Frame-Options` (protección
anti-clickjacking), sin `Content-Security-Policy` (mitigación de XSS/inyección), sin
`Strict-Transport-Security` (anti-downgrade a HTTP), sin `X-Content-Type-Options` (anti MIME-sniffing)
ni `Referrer-Policy`/`Permissions-Policy`. Es una falla de **mecanismo de protección** (CWE-693):
no hay vulnerabilidad de ejecución directa, pero se elimina toda una capa de defensa en profundidad.

## CVSSv3.1 — justificación métrica por métrica

`CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N` → **3.1 (Low)**

| Métrica | Valor | Justificación (por impacto demostrado) |
|---|---|---|
| **AV** | **N** | Respuestas HTTP remotas. |
| **AC** | **H** | El aprovechamiento requiere condiciones extra (una página atacante que enmarque la UI para clickjacking, o contenido que el navegador intente MIME-sniffear). No es explotación directa. |
| **PR/UI** | N / **R** | Sin credenciales, pero necesita que la víctima interactúe (clic sobre el iframe malicioso). |
| **S** | **U** | Dentro de la sesión del navegador de la víctima. |
| **C** | **L** | Impacto acotado: la superficie primaria es una **API JSON** (no hay UI transaccional sensible que enmarcar); el mayor riesgo es la Swagger UI y la ausencia de CSP como amplificador de un XSS futuro. |
| **I/A** | N / N | Sin impacto directo de integridad/disponibilidad. |

> **Por qué LOW (y no Medium):** se puntúa el impacto **demostrado** en esta app. Al ser una API
> JSON sin UI transaccional renderizada, el clickjacking y el MIME-sniffing tienen alcance limitado;
> el valor real de los headers aquí es **defensa en profundidad**, no cerrar una explotación activa.

## PoC (evidencia del DAST del pipeline)

**Baseline (pre-remediación):** el OWASP ZAP del pipeline reportaba la ausencia de todos los headers
(`Content Security Policy (CSP) Header Not Set`, `Missing Anti-clickjacking Header`,
`X-Content-Type-Options Header Missing`, `Strict-Transport-Security Header Not Set`).

**Estado actual (post-remediación, run `30944326920` sobre `main`):** ZAP confirma que los headers
principales ya se emiten; quedan **2 hallazgos Low residuales**:

```
[    Low] X-Content-Type-Options Header Missing            (x3)
[    Low] Cross-Origin-Resource-Policy Header Missing/Invalid (x3)
```

Verificación de que los headers primarios SÍ se emiten (curl sobre un 401):

```bash
curl -sI "http://localhost:8080/api/drivers/search?q=x"
# HTTP/1.1 401
# X-Frame-Options: DENY
# X-Content-Type-Options: nosniff
# Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'
# Referrer-Policy: strict-origin-when-cross-origin
# Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Los 2 residuales aparecen en respuestas que **no atraviesan** la cadena de filtros de Spring Security
con todos los headers (recursos estáticos de springdoc / swagger-ui y la whitelabel error page), y en
que **Cross-Origin-Resource-Policy** no formó parte del set inicial.

## Impact

- **Clickjacking (X-Frame-Options / `frame-ancestors`):** una página atacante podría enmarcar la
  Swagger UI. Acotado (dev-only, sin acciones sensibles).
- **MIME-sniffing (X-Content-Type-Options):** el navegador podría interpretar una respuesta con un
  content-type distinto al declarado.
- **Downgrade (HSTS):** sin HSTS, un MITM podría forzar HTTP. *(HSTS solo se emite sobre HTTPS — en
  el DAST, que corre sobre HTTP, ZAP lo marca; es comportamiento correcto.)*
- **Sin CSP:** un XSS futuro no tendría contención de ejecución de scripts.
- **Defensa en profundidad:** la ausencia elimina una capa completa, aunque hoy no habilite una
  explotación directa.

## Remediation

Se añadió el set completo de headers en `SecurityConfig` (FSEC-17 PR-C, commit `0927e6e`):
`X-Frame-Options: DENY`, CSP restrictiva, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` y HSTS (sobre HTTPS).

> **Conexión con CVE-2026-22732 (Spring Security):** estos headers los **escribe** la maquinaria de
> Spring Security, que tenía el CVE-2026-22732 (fallo en la **escritura de security headers**,
> CWE-425). Remediado por el override a **6.5.9** (ver [ADR-004](../../docs/ADRs/ADR-004-pipeline-gate-strategy.md)
> y `app/pom.xml`). Es decir: la política de headers endurecida se apoya en un motor de escritura ya
> parchado — remediar B-01 sin el fix del CVE habría dejado la propia emisión de headers manipulable.

**Residual (recomendación de hardening, no bloqueante):**
1. Añadir `Cross-Origin-Resource-Policy: same-origin`.
2. Aplicar los headers también a respuestas fuera de la cadena (error page / recursos springdoc)
   vía un `OncePerRequestFilter` global o `server.error` endurecido.

**Test dual (implementado · commit `0927e6e`):**
1. **Presencia:** `InputValidationRemediationTest.securityHeaders_arePresent` — incluso en un `401`
   la respuesta lleva `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, CSP y Referrer-Policy.
2. **Flujo legítimo OK:** el resto de los tests (200/401/403) siguen pasando con los headers activos.
